# 插件后台代理调用与取消

原生插件在事件回调里调用 `agent.run` 做后台整理（自动记忆、自动学习、自动总结）时，宿主和插件各自有时间预算，取消语义也不同。这类调用失败**不等于**删除已有数据，也不该在每轮对话后弹系统通知。

## 两层预算与各自的归因

- **宿主 observe 预算覆盖整次调用，且从调用前开始计时**，包含插件冷启动和 Main 侧会话唤醒；到点会取消授权与调用，插件拿到的 `ctx.signal` 被 abort。它并不读取插件清单里的超时声明。
- **插件本地截止时间只从模型请求开始计时**，比外层预算更短才有意义；两者都会表现为“取消”，混在一起就无法判断该改预算还是改实现。
- 内层先超时但外层后到，错误文本可以是“调用已取消”而不是超时。**本地截止时间必须先结算超时错误再 abort**：`agent.run` 会同步响应 abort，先 abort 会让取消错误赢得竞争，真正的原因被吞掉。

## 取消不是失败

- 关闭/停止会话、用户取消、外层预算到点都属于正常收束：**静默跳过，不写任何结果，不发系统通知**。
- 判断取消要看类型化错误码或 `ctx.signal` 已 abort，不要匹配错误文案；文案随宿主和厂商变化。
- 回调入口先检查 `ctx.signal` 已 abort 就直接返回，避免为一个已失效的上下文继续产生付费模型请求。
- 取消之后仍然要能继续下一轮：不能把“本轮被取消”记成永久失败状态，也不能因此关闭自动整理。

## 通知通道要分开

- **人工触发的整理把错误返回给页面**，用户正在看；不要再弹同一个系统通知。
- **自动整合理由后台发起**，失败需要可见性，但连续相同的失败只按会话在冷却窗口内通知一次；成功时清空冷却，功能保持开启。
- 节流是通知策略，不是错误处理：不能因为节流而丢弃错误本身，也不能用节流掩盖真的数据写入失败。
